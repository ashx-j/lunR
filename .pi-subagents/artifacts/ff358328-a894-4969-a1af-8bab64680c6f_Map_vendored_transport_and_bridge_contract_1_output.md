## Inspection findings

The pinned upstream checkout is `f1c1220`. It is a Python plugin for Hermes, not a provider that lunR can load directly.

- **Blocker, incompatible interfaces.** Upstream `__init__.py:5-6` registers a Hermes `ProviderProfile`. Its client exposes `chat.completions.create(**kwargs)` and OpenAI-shaped responses in `directsdk.py:364-437,622-627`. lunR requires a `streamSimple(model, context, options)` handler returning an `AssistantMessageEventStream`, with its own message, tool, usage, and terminal-event types in `packages/coding-agent/src/core/provider-composer.ts:43-61,447-465` and `packages/ai/src/types.ts:390-483`. The Python client also imports Hermes `agent.*` and `tools.*` modules in `directsdk.py:141,179` and `__init__.py:20`. Copying the plugin into an npm package would not make it runnable.
- **High, authentication needs its own route.** The plugin delegates credentials entirely to the official `claude` executable. `directsdk_setup.py:49-67` probes `claude auth status`; it neither stores nor refreshes an OAuth token. lunR's extension OAuth contract instead persists token-shaped credentials and converts them to an API-key string in `packages/coding-agent/src/core/provider-composer.ts:222-247`. lunR's model picker also restricts availability to stored credentials or configured keys in `packages/coding-agent/src/core/model-runtime.ts:321-345`. A fabricated key or the existing `anthropic` API route would misrepresent this authentication method. Keep subscription and API-key providers separate.
- **High, one-request admission is essential.** Each upstream call launches a fresh `claude -p` in a private directory, disables native tools/settings/approvals and native compaction, then replays history over stream-json. `directsdk.py:438-535` installs an inert MCP tool manifest. `admission.py:77-101,134-198` permits one `/v1/messages` request through a request-scoped loopback relay and denies subsequent native recovery requests. `directsdk.py:551-621` publishes tools only after complete response, usage, and exit validation. A bridge that merely launches `claude -p --max-turns 1` loses that admission guarantee.
- **High, replay cannot be mapped by text alone.** `directsdk.py:58-135,594-609` retains ordered native assistant blocks and signed thinking in a versioned carrier, but replays canonical blocks if the host edits assistant content or calls. lunR's `ThinkingContent.thinkingSignature` exists, yet its `AssistantMessage` has no equivalent carrier for ordered native assistant messages in `packages/ai/src/types.ts:326-379,390-407`. Tool-result ordering and host compaction need explicit round-trip tests.
- **Medium, native boundaries need translation.** Upstream only accepts unique tool names matching `[A-Za-z0-9_-]{1,50}`, normalizes tool schemas, supports base64 images, limits request fields, and maps final usage and stop reasons in `directsdk.py:141-247,594-627`. lunR uses TypeBox tool parameters, `toolResult` messages, `toolUse` stop reasons, and an event stream in `packages/ai/src/types.ts:301-483`. Native list-price accounting is **not** a subscription invoice, as `__init__.py:21-40` explicitly records.

Setup returns `{available, logged_in, plan, detail, login_command}`. `discover_models()` returns `{id, label, note, upstream_requests}[]` or `None` after a signed-in CLI `initialize` handshake; failure falls back to pinned models. See `directsdk_setup.py:49-115` and `model_catalog.py:2-45`. Discovery verifies zero *Messages* requests, not a universal offline guarantee. The request path rejects inherited conflicting Anthropic API-key and backend environment settings, resolves the Windows `claude.cmd` shim, and kills its process tree on cancellation in `directsdk.py:265-310,438-483`.

**Realistic integration:** Port the transport and admission behavior to TypeScript, register a distinct lunR provider with a custom stream handler, and add CLI-backed external-process availability/login handling. Preserve lunR's ownership of tools, permissions, sessions, and compaction. Retaining the Python code instead requires shipping a Python runtime plus compatible Hermes core; upstream's `pyproject.toml` declares no Python dependencies, but its imports and `conftest.py:8-21` demonstrate that Hermes core is required. The npm artifact currently ships `dist` and selected assets, not the upstream plugin, in `packages/coding-agent/package.json:20-38`; the Node build bundles compiled JS in `scripts/build-node-runtime.mjs:1-47`.

Upstream's documented test command is `python -m pytest -q` with `HERMES_AGENT_REPO` pointing to a Hermes checkout. `.github/workflows/tests.yml:8-31` installs Hermes and runs the suite on Linux, macOS, and Windows. The checkout contains 18 named test functions covering admission, replay, setup, discovery, models, and subprocess lifecycle. I did **not** run them: the read-only Plan-mode command gate blocked even `python -m pytest --version`, and the suite requires Hermes core. No live account or native CLI qualification was performed.
