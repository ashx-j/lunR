## Gateway and installer findings

- **Blocker:** `packages/coding-agent/src/gateway/index.ts` implements a Telegram/Discord bot daemon, pairing, and status. It has no `gateway setup`, `start`, `stop`, or `doctor` commands, no network listener for an interactive TUI, and no OS service. A remote-session host should be a separate CLI route, not another chat adapter.
- **Blocker:** `packages/coding-agent/src/core/install-features.ts` offers a chat-platforms `autostart` option but explicitly says the login item is not installed in this build. Do not present that setting as working remote hosting.
- **Blocker:** `packages/coding-agent/src/gateway/agent-bridge.ts` creates independent headless sessions using the daemon's `process.cwd()`. `packages/coding-agent/src/gateway/store.ts` persists chat-to-session-file mappings so bots can reopen conversations. Neither attaches to an already running TUI session. Reusing this bridge would break the requirement for the *exact* live session across devices.
- **High:** `packages/coding-agent/src/cli/install-cli.ts` can remove the installation and optionally purge the agent directory without stopping a service; `packages/coding-agent/src/cli/update-cli.ts` reinstalls the global npm package without coordinating a running process and warns that Windows may refuse to overwrite files. Service-aware stop, update, restart, and uninstall must precede shipping autostart.
- **Medium:** `packages/coding-agent/src/gateway/config.ts` writes bot-token config to a temporary file before applying best-effort `0600` to the renamed file; Windows ACL protection is explicitly best-effort. Do not copy this storage procedure for remote device credentials or private keys.

Useful integration points are the early command dispatch in `packages/coding-agent/src/main.ts`, deferred non-TUI command routing in `packages/coding-agent/src/startup/launch-routing.ts`, package/bin definition in `packages/coding-agent/package.json`, and install-location metadata in `packages/coding-agent/src/core/install-layout.ts`. The published npm package is already one `lunr` CLI on Node 22.19+, with no separate host edition. `packages/coding-agent/docs/features.md`, `docs/quickstart.md`, and `docs/security.md` need distinct bot-gateway versus remote-session explanations. Security docs correctly warn that the agent has the host user's filesystem and shell authority.

## Recommended host and setup design

Run one opt-in, unprivileged **remote-session host** per user. The host owns the canonical live session; local and remote TUIs attach to it rather than independently opening its session file. This ownership change belongs to the runtime/protocol work, not the gateway bridge. Keep remote credentials and device approvals separate from Telegram/Discord bot pairing.

Offer `lunr remote setup`, `host start|stop|status|doctor`, and `connect` in the same package. Setup first explains the host's authority, checks OS and network prerequisites without changing them, offers **Tailscale** or **self-hosted WireGuard**, then asks separately before installing VPN software, changing VPN configuration, opening a firewall rule, or enabling sign-in autostart. Never run a privileged installer or alter router settings through an implicit `--yes`. Use official installers and user-visible authentication; do not collect a Tailscale account password. Keep private keys and provider credentials out of command arguments, service definitions, diagnostic output, and client devices.

Default to a VPN-only listener plus **application-level, per-device authentication**. Pin the host identity at pairing, require explicit host approval for a new client, allow revocation, and use an encrypted, authenticated application connection on either VPN. A VPN membership check alone does not authorize shell-capable lunR sessions. Scope network access to the host port; never expose the listener on the public interface. Tailscale Serve is an optional localhost-to-tailnet HTTPS route, but it requires tailnet HTTPS setup and must never be confused with public **Funnel**. Its identity headers require a localhost-only backend and still should not replace lunR's device authorization. [Tailscale Serve](https://tailscale.com/kb/1312/serve), [tailnet access controls](https://tailscale.com/kb/1337/acl-syntax).

Tailscale is the easiest path: guide installation and signing both machines into the same tailnet, verify connectivity and a restricted access rule, then pair the lunR client. Its relays can carry encrypted traffic when NAT blocks direct connections, without requiring the user to purchase a server. The Personal plan currently advertises free use for six users, but it remains a third-party coordination and possible relay dependency. [Quickstart](https://tailscale.com/kb/1017/install), [DERP behavior](https://tailscale.com/kb/1232/derp-servers).

For self-hosted WireGuard, generate independent device keys locally and guide users through peer configuration, narrow `AllowedIPs`, and a reachable UDP endpoint. Check whether the host has public IPv4, usable IPv6, or control of router port forwarding **before** promising access outside the LAN. `PersistentKeepalive` helps maintain an existing NAT mapping; it does not manufacture a reachable endpoint behind CGNAT. If both peers lack reachable endpoints, explain that an independently reachable relay/server or another network arrangement is necessary; “no paid infrastructure required” cannot mean universal connectivity with self-hosted WireGuard. Official downloads differ on Windows, macOS, and Linux. [WireGuard install](https://www.wireguard.com/install/), [endpoint and keepalive configuration](https://www.wireguard.com/quickstart/).

For autostart, install only after separate consent:

| OS | Sign-in mechanism | Limit |
|---|---|---|
| Windows | Current-user Task Scheduler logon trigger, limited privileges, managed task identity, single instance and restart policy | A sign-in task is not a promise of availability before login. Avoid stored account passwords and administrator execution unless separately justified. [Logon trigger](https://learn.microsoft.com/en-us/windows/win32/taskschd/starting-an-executable-when-a-user-logs-on), [logon types](https://learn.microsoft.com/en-us/windows/win32/taskschd/principal-logontype) |
| macOS | User-owned `~/Library/LaunchAgents` plist with `ProgramArguments`, launch-on-login and controlled restart | A LaunchAgent ends at logout; a system LaunchDaemon would be a separate privileged product decision. [Apple launchd guide](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/CreatingLaunchdJobs.html) |
| Linux | `systemd --user` unit enabled for the user | Ordinary user units may stop after the final logout. Offer `loginctl enable-linger` only as a separately explained, permission-gated option when post-logout hosting is wanted. [loginctl](https://freedesktop.org/software/systemd/man/latest/loginctl.html), [systemd services](https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html) |

Service definitions should reference a stable, validated launcher and explicitly recorded agent directory and working-directory policy. They should not depend on the shell's interactive `PATH` or contain secrets. Make installation idempotent, verify ownership before replacing a unit/task, and remove only lunR-owned artifacts. Updates need a bounded drain and restart, protocol-version compatibility check, rollback/error reporting, and special care for Windows file replacement. Uninstall must stop and disable hosting **before** deleting its executable; preserve sessions and credentials by default, and make key/device-data purge a distinct confirmed choice.

Sleep, shutdown, VPN sign-out, and offline periods interrupt the connection. Preserve the canonical session locally, reconnect with bounded backoff and resynchronization, and show “host asleep/offline” rather than promising uninterrupted execution. On waking, recheck interface binding, authorization, and service health. A closed terminal must not stop the opted-in host.

Implementation phases: establish single-owner session attachment and security invariants; add a foreground host with explicit pairing; implement the Tailscale setup and network diagnostics; add WireGuard guided configuration; add each OS's service lifecycle; then service-aware update/uninstall and docs. Test protocol and service-file generation on all three OSes, plus real sign-in, terminal close, reconnect, sleep/wake, VPN disconnect, key revocation, update, and uninstall. **Code paths intended for all three operating systems are not evidence of testing on all three.** This read-only review ran on Windows and did not install or exercise any service or VPN.
