## Recommendation

Put a persistent host inside the existing lunR package. When remote operation is enabled, both the local TUI and a laptop client should attach to a session owned by that host. The host should keep one isolated worker process per active session and remain alive when either client disconnects. This preserves the exact running agent, including its current turn. Opening the session JSONL file on the laptop would only reconstruct saved history.

Use the existing RPC command and event types as a starting point for the worker connection, but **do not expose the current stdin/stdout RPC process directly as the remote endpoint**. The host needs its own authenticated, reconnectable client protocol. Each installation can run the same host and client code; there is no need for a separate host product.

The relevant documented contracts are in `docs/sdk.md`, `docs/rpc.md`, `docs/sessions.md`, `docs/session-format.md`, `docs/features.md` and `docs/interactive-startup.md`. `core/agent-session-runtime.ts:73-180,402-410` is the right lifecycle boundary: shutdown hooks run before disposal, and replacement creates a new session object. The daemon must own that boundary, not an attached terminal.

## Scoped implementation plan

1. **Establish ownership.** Add a host command and host-side session registry in this package. Give each running session one worker, one writer and a stable host-plus-session identity. Have local remote-enabled launches attach through the host from their first turn. Keep ordinary standalone CLI behavior available; a standalone process cannot be turned into an already-hosted live process merely by reopening its file.
2. **Separate clients from workers.** The host retains worker pipes while local and remote clients connect and disconnect. Reuse `AgentSessionRuntime` and RPC command/event types inside the worker. Add authenticated attach, observer versus controller rights, explicit control transfer, host-side command ordering and bounded event delivery. Never forward an arbitrary client-supplied `switch_session` path without host-side authorization.
3. **Make reconnect deterministic.** Send a coherent snapshot with host generation, session identity, active leaf, state, completed entries, pending UI requests and a monotonically increasing event sequence. Then replay events after that sequence. If the cursor is too old or the host generation changed, require a fresh snapshot. Journal accepted mutating command IDs before dispatch so a retransmitted prompt cannot silently run twice. On uncertain worker-crash outcomes, report uncertainty rather than replaying a tool call that may already have modified files.
4. **Route unattended decisions.** Keep approval requests with the session worker, give them IDs and deadlines, and route replies only from its authorized controller. Disconnect must neither grant approval nor destroy the running turn. Define whether the request waits for controller reconnection or expires with rejection. Preserve the existing manual and large-subagent fail-closed behavior.
5. **Consolidate background ownership.** Run one cron scheduler per installation, with the host as owner when hosting is enabled; explicitly disable or coordinate the TUI and gateway scheduler paths. Keep detached subagents tied to their worker's stable session identity, restore watchers on restart and avoid duplicate result delivery. Existing gateway chat conversations can remain separate initially; merging them into the hosted-session registry is a later, deliberate change.

The worker boundary is worth keeping even though direct in-process `AgentSession` use would be simpler initially. It contains process-global extension bridges and approval handlers, permits independent cwd and extension loading, and prevents one session's crash from terminating every hosted conversation. It is **not** a security sandbox for untrusted code.

## Focused acceptance tests

- Start a session locally, begin a long turn, disconnect its TUI, attach from another client and observe that **the same worker and turn** continue. Reattach after a network interruption without duplicate messages or tool execution.
- Reconnect across `/new`, switch, fork and tree navigation. Verify active identity and leaf, including a branch selection with no subsequent append.
- Retransmit a prompt after losing its acknowledgment. Verify one acceptance or an explicit uncertain-outcome response, never silent double execution.
- Request a manual approval, disconnect the controller, then reconnect or let its deadline expire. Verify unauthorized observers cannot approve and no offline default grants permission.
- Complete an async subagent while all clients are detached. Verify the originating session receives its result once on reconnection.
- Start host, TUI and optional gateway against the same cron store. Verify one scheduler owns each due job and worker failure does not cause an unreported second execution.

The largest unresolved product decision is crash recovery. **Continuous attachment is achievable while the host worker lives.** After that worker or machine dies, saved history can reopen, but an interrupted model request or external tool effect cannot be resumed as the exact running computation. The UI should label that case as recovered history with an interrupted turn, not claim seamless continuation. A second decision is whether a controller's offline approval waits for reconnection or times out; either can be safe if the timeout always rejects.
