## Desktop capability map

**Scope:** A local Windows desktop app should use lunR's existing runtime, not emulate its TUI or reimplement agent behavior. `REMOTE_DESKTOP_HANDOFF.md` places the desktop app after TUI work and the separately downloaded remote host after desktop work. The remote-device gateway is therefore a placeholder in this plan. The existing Telegram/Discord gateway stays.

### Integration findings

- **Blocker: RPC is not desktop feature parity.** `src/modes/rpc/rpc-mode.ts` exposes prompts, steering, model/thinking changes, session/tree data and basic extension dialogs. Its `get_state` has no permission-mode, goal, cron or subagent state; `get_commands` excludes built-in TUI commands; `src/core/slash-commands.ts` and `src/modes/interactive/interactive-mode.ts` own many of those actions. `docs/rpc.md` explicitly says built-in TUI commands cannot be invoked through RPC `prompt`. `rpc-mode.ts` also makes `custom()` unavailable, ignores component widgets and custom footer/editor, and does not support autocomplete composition. A desktop protocol needs typed actions, state snapshots and events for the built-ins rather than command-string or terminal-output parsing.
- **High: approval ownership needs design before implementation.** `src/core/permissions.ts` registers an approval handler and treats `present_plan` specially: with no handler it reports that the user will review later, while mutating tool gates fail closed. Desktop process/view disconnects must have an explicit pending-approval policy. The graphical client must not silently turn an absent approval UI into consent.
- **High: runtime lifetime is not view lifetime.** `src/modes/rpc/rpc-mode.ts` disposes its runtime on shutdown. Reopening a saved JSONL session restores history, not an in-flight tool, approval dialog or child. The local desktop process boundary needs ownership and reconnect behavior; the later remote host must reuse that runtime rather than fork it.
- **Medium: TUI-specific bridges need structured replacements.** `src/builtin-extensions/index.ts` distinguishes light and deferred features; `ashxj-tui.ts` owns footer customization, `lunr-cron.ts` checks `"tui"` before starting its scheduler, and subagent/intercom/MCP interfaces include `ctx.ui.custom()` components. Audit each built-in's interaction and lifecycle as it moves to graphical mode. Do not promise graphical support for third-party custom TUI components; the requested scope is built-ins.
- **Medium: clarify browser scope.** `pi-web-access/index.ts` supports an interactive browser curator and `pi-mcp-adapter/ui-session.ts` supports browser-hosted MCP UI. Neither establishes first-party browser automation or native computer use. Treat those as separate product requirements if intended.

**Focused validation for the eventual implementation:** Add contract tests for typed desktop state/actions against the same runtime as the CLI; approval timeout/disconnect and plan feedback; single-owner cron firing while desktop and bot gateway coexist; subagent question/answer/stop/reconnect ordering; OAuth and MCP elicitation through the graphical dialog channel; session undo versus file rollback; and graphical rendering of streamed tools, thinking, images, todos and usage. Existing useful baselines include `test/{rpc,permissions,plan-approval,gateway-cron,supervisor-question-lifecycle,subagent-escape,interactive-mode-undo-edit,rollback,agent-memory,usage-view}.test.ts`. **No tests were run** for this read-only mapping.

The product choices worth settling are whether desktop owns a persistent local runtime after its window closes, how it arbitrates cron ownership with a running bot gateway, and whether "browser" requires agent-controlled browsing beyond the existing curator and MCP interfaces. Remote-device gateway packaging and pairing can wait for its later milestone.
